    21→## 1. Verified parameter-count formula
    22→
    23→Architecture (from `transformer.py`, config verified against `config.json`): decoder-only, learned positional embeddings, Pre-Norm blocks, RMSNorm (weight only, no bias), attention as a fused QKV linear + output projection, FFN = two linears with hidden = `ffn_mult * C`, manual GELU-tanh, LM head without bias, `bias=True` on all block linears, weight tying ON.
    24→
    25→With `V` = vocab_size, `T` = block_size, `L` = n_layer, `H` = n_head, `C` = n_embd (head_dim = C/H), `b` = 1 if bias else 0:
    26→
    27→```
    28→Per transformer block:
    29→  ln1 (RMSNorm)          : C
    30→  qkv  Linear(C, 3C)     : 3*C^2 + 3b*C
    31→  proj Linear(C, C)      :   C^2 +   b*C
    32→  ln2 (RMSNorm)          : C
    33→  fc   Linear(C, 4C)     : 4*C^2 + 4b*C
    34→  proj Linear(4C, C)     : 4*C^2 +   b*C
    35→  ---------------------------------------
    36→  per layer              : 12*C^2 + (2 + 9b)*C        (b=1 here → 12*C^2 + 11*C)
    37→
    38→Model total (weight tying ON, lm_head shares tok_emb):
    39→  P = V*C          (token embedding, also serves as LM head)
    40→    + T*C          (learned positional embedding)
    41→    + L*(12*C^2 + (2+9b)*C)
    42→    + C            (final RMSNorm)
    43→```
    44→
    45→If weight tying were OFF, add `V*C` (untied LM head, no bias). If norm were LayerNorm instead of RMSNorm, each of the 3 norms would gain a bias (+2C per block, +C final).

   116→## 4. Stage-by-stage estimates and justification
   117→
   118→### 4.0 Throughput model used for all wall-clock estimates (ESTIMATE method)
   119→
   120→Measured anchor: 5,234.3 tok/s at 6N/token = 8.10 MFLOP (Stage 0) ⇒ ~42.4 GFLOP/s achieved (6ND basis) on 2 CPU cores.
   121→
   122→Model: `tok/s(stage) ≈ 5,234 * (N0/N) * u`, where `u` is a utilization-retention factor around the FLOP-inverse prediction:
   123→
   124→- FLOP-inverse prediction (u=1): Stage 1 ≈ 1,396 tok/s; Stage 2 ≈ 443 tok/s; Stage 3 ≈ 142 tok/s (per-token FLOPs grow 3.75x / 11.8x / 37.0x).
   125→- u < 1 accounts for cache pressure at C ≥ 256, deeper sequential stacks, the quadratic attention term at T = 512/1024, and smaller micro-batches (Stage 2 batch 4, Stage 3 batch 1). u > 1 is possible for Stage 1 (wider GEMMs use BLAS better than C=128), capped conservatively.
   126→- Bands used: **Stage 1 u ∈ [0.5, 0.9] → 700–1,250 tok/s; Stage 2 u ∈ [0.4, 0.8] → 180–350 tok/s; Stage 3 u ∈ [0.3, 0.7] → 42–100 tok/s.** (All wall-clock figures below are derived from these exact bands.)
   127→
   128→Why a naive "0.5–0.75x per stage" multiplier is rejected as unphysical: 5,234 * 0.75^3 ≈ 2,208 tok/s at Stage 3 would imply 2,208 * 299.3 MFLOP ≈ 660 GFLOP/s on 2 CPU cores — about 7x the theoretical AVX2-FMA peak of such a machine (~96 GFLOP/s) and 16x what was actually measured. Throughput must fall roughly in proportion to per-token FLOPs; the ranges above are FLOP-consistent.
   129→
   130→FLOPs formula: `≈ 6*N*D` (forward+backward, weight-term dominant), plus the causal-attention term making true FLOPs `≈ 6*N*D * (1 + T/(6C))`: factor 1.167 (Stage 1), 1.222 (Stage 2), 1.333 (Stage 0 and 3). With tying, the embedding-lookup saving and the tied-LM-head matmul cancel in 6ND exactly. The 6ND numbers in tables are the conservative lower bound.
   131→
   132→RAM formula (fp32 pipeline, AdamW, as implemented in `trainer.py`):
   133→
   134→```
   135→R_peak ≈ 16*N                    (fp32 weights 4N + grads 4N + exp_avg 4N + exp_avg_sq 4N)
   136→       + A                       (activations saved for backward)
   137→       + ~0.4–0.6 GB             (PyTorch runtime, allocator, memmapped data)
   138→A ≈ L * 4B * (19*T*C + 3*H*T^2)  (per-layer saved tensors incl. 2–3 copies of the
   139→                                  B*H*T*T attention matrix; manual attention, no flash)
   140→  + 12*B*T*V                     (logits + log-softmax + grad)
   141→```
   142→
   143→Safety rule for this machine: keep `R_peak ≤ 2.5 GB` (headroom for OS, monitoring, periodic eval).
   144→
   145→### 4.1 Stage 1 — Intermediate-5M (ESTIMATE)
   146→
   147→**Config: V=4096, T=256, L=5, H=4, C=256, ffn_mult 4 → 5,060,608 params.**
   148→
   149→Justification: tokenizer, vocab, block size, corpus, batch, and schedule length stay IDENTICAL to EXP-001; only model shape changes. This isolates the parameter-scaling variable on fixed data and keeps perplexities directly comparable (same tokenizer, same held-out split). head_dim rises 32 → 64 (the standard empirical choice; keeping H=4 avoids per-head CPU overhead). Depth +1 (5 vs 4) is the minimal change that lands at ~5M: with C=256 and L=4 the count would be 4,271,360; L=5 gives 5,060,608.
   150→
   151→- **Tokens:** primary run D = 2,457,600 tokens, byte-identical schedule to EXP-001 (10.7 epochs of the 230K train split — repetition-heavy, flagged honestly). Chinchilla-style 20 tokens/param would want ~1.0e8 tokens; that data does not exist and must not be pretended. Optional secondary probe: D = 5M (~21.7 epochs) to measure whether more repetition still buys valid loss at 4x capacity. Published data-constrained scaling results say repeats up to ~4 epochs are nearly as good as fresh data and value decays thereafter — the primary run is already beyond that, which is exactly why its purpose is the scaling coefficient, not data scaling.
   152→- **RAM:** 16N = 81 MB states; A ≈ 426 MB at batch 8 (L=5: 5 x 65 MB + 101 MB logits); total ≈ 1.0–1.3 GB. Verdict: comfortable.
   153→- **FLOPs:** 6ND = 7.46e13 (D=2.46M) / 1.52e14 (D=5M); true ≈ x1.167.
   154→- **CPU wall-clock:** 0.5–1.0 h (primary) / 1.1–2.0 h (probe) at 700–1,250 tok/s.
   155→- **GPU (if rented for a day of batch runs):** < 1 minute per run; irrelevant locally.
   156→- **Checkpoint:** ~61 MB (12 B/param + overhead); x2 seeds ≈ 122 MB.
   157→- **Eval protocol:** identical held-out protocol (valid split, batch 8, eval_batches 12, fixed eval seed) PLUS first use of the two-seed reproducibility check (seeds 42 and 1337) and the fixed generation-rubric prompt suite (Section 5.4). Test split still untouched.
   158→- **Verdict: FEASIBLE on the current 2-CPU / 3.95 GB machine.** This is the next run to execute.

   160→### 4.2 Stage 2 — Intermediate-15M (ESTIMATE; requires data expansion FIRST)
   161→
   162→**Config: V=4096, T=512, L=8, H=6, C=384, ffn_mult 4 → 15,959,424 params.**
   163→
   164→Justification: block 256 → 512 is now justified by data — with ≥ 10M unique tokens, documents longer than 256 tokens become frequent, and 529 train blocks would no longer be the binding constraint (the current corpus cannot even fill a 512-block set without heavy overlap). head_dim stays 64 (384/6). Depth 8 gives a depth-rich shape with known precedent at this scale (e.g. ~10M-param public baselines use 6L/384d; 8L adds the register needed for morphology-heavy Arabic). Vocab stays 4096 deliberately: keeping the tokenizer frozen across Stages 0–2 makes valid-loss/perplexity numbers directly comparable across the whole ladder; a vocab change would break the series. The 8192-embedding variant (adds ~3.1M params) is available if analysis shows 4096-vocab fragmentation hurting, at the cost of comparability.
   165→
   166→- **Tokens:** Chinchilla reference 20 tokens/param ≈ 3.2e8. Data-constrained plan with a ≥ 10M-unique-token corpus: D = 50M min (5 epochs), **100M recommended (10 epochs)**, cap ~320M (32 epochs; beyond ~16 epochs of repeated data, marginal value decays). If the corpus reaches 30M unique, 100M processed = 3.3 epochs — the preferred regime.
   167→- **RAM:** 16N = 255 MB states. Batch 8: A ≈ 2.37 GB → total ≈ 3.1 GB: risky against 3.95 GB. **Batch 4 + grad_accum 2 (same effective batch 8, supported by `TrainingConfig.grad_accum`): A ≈ 1.18 GB → total ≈ 1.9–2.0 GB. Verdict: feasible with the reduced micro-batch.**
   168→- **FLOPs:** 6ND = 4.79e15 / 9.58e15 / 3.06e16 for D = 50M / 100M / 320M; true ≈ x1.222.
   169→- **CPU wall-clock:** 1.6–3.3 d / **3.3–6.5 d** / 10.5–20.9 d at 180–350 tok/s. The recommended 100M-token run means ~4–7 days of exclusive machine occupancy — accepted explicitly at the gate, not discovered mid-run. Checkpoint-every-300-steps retention policy: keep latest + best only (disk bound).
   170→- **GPU:** 5–20 min for D=100M at 10–40 TF/s effective; minutes even at conservative MFU.
   171→- **Checkpoint:** ~192 MB; x2 seeds ≈ 384 MB.
   172→- **Eval protocol (extends Stage 1):** same held-out protocol; ADD per-register perplexity for MSA / dialect / English (requires register tagging at ingest — current `dataset_stats.json` records ar/en/mixed only; minimum 5,000 held-out tokens per register, smaller registers reported with an explicit small-sample flag and never averaged into a headline number); generation rubric on the fixed prompt suite; two-seed reproducibility; train-valid gap ≤ 0.8 guard.
   173→- **Verdict: FEASIBLE on the current machine** (with batch 4 + accum 2, and with the machine dedicated for ~4–7 days). Also trivially feasible on any rented GPU if the owner prefers not to tie up the box for a week.

   175→### 4.3 Stage 3 — SYRIA AI Nano ~50M (ESTIMATE; requires data pipeline scaled + cloud GPU)
   176→
   177→**Config: V=16384, T=1024, L=13, H=8, C=512, ffn_mult 4 → 49,881,088 params ≈ 49.9M.**
   178→
   179→Justification: T=1024 and V=16384 preserve the planned Nano intent (config.py preset uses T=1024, V=16384); C=512 keeps head_dim 64; L=13 instead of the preset's L=8 is the single change needed to genuinely reach the advertised 50M (preset L=8 computes to 34.1M — Section 1.2). The vocab increase 4096 → 16384 is justified only now: at 50M params the embedding is 16.8% of the model (tok_emb share; at Stage 0 it was 38.9%), a 16K BPE cuts Arabic token fertility (longer effective context per document), and a ≥ 100M-token corpus can support 16K merges without fragmentation. Cost: token-level perplexity stops being comparable to Stages 0–2 — mitigated by reporting bits-per-character alongside perplexity from Stage 3 onward (Section 5.4).
   180→
   181→- **Tokens:** Chinchilla reference 20 tokens/param ≈ 1.0e9. Data-constrained plan with a ≥ 100M-unique-token corpus: D = 0.3B min, **0.5–1.0B recommended (5–10 epochs)**.
   182→- **RAM:** 16N = 798 MB states. Batch 1 + grad_accum 8: A ≈ 2.03 GB (13 layers x 140.5 MB, incl. 3 x B*H*T*T fp32 attention tensors at T=1024 — the manual attention materializes 8 x 1024 x 1024 matrices; no flash attention in this codebase) + 201 MB logits → total ≈ 3.3–3.6 GB vs 3.95 GB available. Memory-verdict: borderline; < 15% headroom, fragmentation-prone, no room for concurrent eval/monitoring. **Compute-verdict is what actually kills it (below).**
   183→- **FLOPs:** 6ND = 8.98e17 / 1.50e17 / 2.99e17 for D = 0.3B / 0.5B / 1.0B; true ≈ x1.333.
   184→- **CPU wall-clock:** 35–82 d / 58–136 d / **117–273 d** at 45–100 tok/s. Even the most optimistic corner (0.3B tokens at 100 tok/s) is over a month of a fully occupied, thermally stressed 2-core box with zero resilience to interruption. **Verdict: NOT FEASIBLE on this machine.**
   185→- **GPU (24 GB cloud instance):** the code must first be moved to GPU with AMP/bf16 or TF32 enabled (currently fp32-only; `pick_device` already supports CUDA). Effective throughput for a 50M fp32-from-scratch codebase at modest MFU: 10–40 TF/s → 0.8–3.3 h (0.3B), 1.4–5.5 h (0.5B), **2.8–11.1 h (1.0B)**. If the optimistic 100–200 TF/s effective were truly sustained: 33–66 min for 1.0B. Plan on the conservative band; even x5 slack keeps this a 1–2 day rental.
   186→- **Checkpoint:** ~601 MB full training checkpoint; ~200 MB fp32 inference weights. Two-seed package ≈ 1.6 GB. Trivial disk cost.
   187→- **Eval protocol:** full pack — held-out protocol, per-register PPL (MSA/dialect/English), bits-per-character (cross-vocab comparability), generation rubric, two-seed reproducibility on GPU, gradient-flow check on 100% of 49.9M params, plus documented limits (ROADMAP Phase 6 gate).
   188→- **Verdict: CANNOT run on the current 2-CPU / 4 GB machine (compute-infeasible; memory borderline). CAN run on one modest cloud GPU (hours, not weeks) — but only after the data gate (≥ 100M unique tokens) and numerics-parity gate pass.**

   192→## 5. Scientific rationale per stage — what each run tests
   193→
   194→### 5.1 Stage 1 (5M, same data): the fixed-data scaling point
   195→
   196→Hypothesis H1: on byte-identical data and schedule, a 3.75x model reduces valid loss by ≥ 3% relative. This measures the project's first own scaling coefficient (dLoss/dlogN at fixed D) and validates the pipeline at 4x size. Honest expectation: the improvement will be MODEST, because the 230K-token corpus is the binding constraint, not capacity. If Stage 1 valid loss ≈ Stage 0 valid loss, that null result is itself the finding: the data ceiling has been reached, and the correct next investment is data, not parameters.
   197→
   198→### 5.2 Stage 2 (15M, 10M+ tokens): the data-boundary experiment
   199→
   200→Hypothesis H2: with data expanded ~40x (230K → ≥ 10M unique tokens), a ~16M model at 512 context improves valid loss ≥ 3% over Stage 1 AND shows a smaller train-valid gap (less repetition, more fresh tokens). This run separates "bigger model on starved data" from "bigger model on adequately-fed data" — the two confounds Stage 1 deliberately could not separate. Block 512 tests whether longer context helps on this corpus (measured via valid loss and register PPLs, not assumed).
   201→
   202→### 5.3 Stage 3 (Nano-50M, 100M+ tokens): full Nano only after the data pipeline scales
   203→
   204→Hypothesis H3: a ~50M model trained on ≥ 0.5B tokens (~20:1 Chinchilla-style reference) reaches substantially lower per-register perplexities and coherent short generations, and the ladder's loss-vs-N curve is consistent enough to extrapolate beyond 50M. Nano is explicitly gated on the corpus, because of the memorization regime:
   205→
   206→**Explicit statement: increasing model size without increasing data will NOT improve validation loss beyond a point.** A larger model memorizes a small corpus better, which lowers TRAIN loss while valid loss stalls or worsens. EXP-001 already repeats its 230K-token train split 10.7x and shows valid > train. This is why data expansion precedes Nano in this plan, and why Stage 2's entry gate is a data quantity, not a parameter count.
   207→
   208→### 5.4 Evaluation protocol (common to all stages, additive)
   209→
   210→1. Held-out valid loss, same protocol as EXP-001 (batch 8, eval_batches ≥ 12, fixed eval RNG, best-valid tracking); test split touched only at stage close-out.
   211→2. Two-seed reproducibility: seeds 42 and 1337; |Δ valid| ≤ 0.05 gate; loss-curve overlays archived per experiment (log.jsonl already exists).
   212→3. Per-register perplexity: MSA / Syrian-dialect / English, each ≥ 5,000 held-out tokens (or flagged as small-sample); requires adding register tags to the corpus pipeline (currently only ar/en/mixed are recorded).
   213→4. Generation rubric: fixed 10-prompt suite (MSA, dialect, English, code — mirroring EXP-001's archived prompts), greedy + temperature 0.8 / top-k 50, human-scored 1–5 (fluency, coherence, register fit), archived as evaluation_results.json per stage for longitudinal comparison.
   214→5. Overfit guard: train-split − valid gap ≤ 0.8 (EXP-001 baseline: −0.41, i.e. model underfits; watch the sign flip as data grows).
   215→6. Regression suite (currently 34/34 pytest + gradient-flow-on-all-params selftest) must pass before any stage is declared done.
   216→7. From Stage 3: bits-per-character reported alongside PPL because the vocab change breaks token-PPL comparability.

   253→## 7. Non-feasibility honesty — Nano-50M on this machine
   254→
   255→**Plain statement: SYRIA AI Nano (~50M) cannot be trained on this 2-logical-core, ~3.95 GB RAM, no-GPU machine.** Reasons, in order of severity:
   256→
   257→1. **Compute (decisive):** 117–273 days of continuous CPU time for the recommended 0.5–1.0B tokens; even a minimal 0.3B-token run is 35–82 days. Throughput would be ~45–100 tok/s (ESTIMATE, FLOP-consistent with the measured 5,234 tok/s baseline), and the machine would be unusable for anything else for months, with near-certain interruption.
   258→2. **Memory (borderline):** at batch 1 + grad accum 8 the estimate is 3.3–3.6 GB vs 3.95 GB available — under 15% headroom, fragmentation-prone, no room for concurrent evaluation. Not the binding constraint, but not comfortable either.
   259→3. **Engineering reality:** the current trainer is fp32-only CPU-first; it has no flash attention, no gradient checkpointing, and no AMP — none of which would rescue the compute budget on 2 cores anyway.
   260→
   261→Options, honestly costed (ESTIMATE ranges; nothing here is promised):
   262→
   263→| Option | What it gives | Cost / risk |
   264→|---|---|---|
   265→| (a) Rent ONE 24 GB cloud GPU when the data gate passes | Nano 1B-token run in ~3–11 h; full gate package (parity + 2 seeds + reruns) in 1–2 days | ~$20–200 total including retries and seed repeats: 24 GB class at typical $0.30–0.80/h; an A100 40GB at $1.00–2.00/h is ~2x the hourly rate but ~2x faster, so totals are similar. Requires the AMP/TF32 parity change, validated by gate G3.2 |
   266→| (b) Stay at Intermediate-15M until resources exist | A legitimate, publishable model on 10–30M tokens; the ladder's scientific value is already realized by Stage 2 | Zero cost; recommended default if the corpus cannot reach 100M tokens |
   267→| (c) Model / pipeline parallelism on this machine | Nothing useful | NOT worth it: 50M params fit in one 24 GB GPU 100x over; pipelining across 2 logical cores adds overhead where there is no bandwidth to hide it. Rejected. |
   268→| (d) "Nano-lite" (~15–25M trained longer) on CPU | A middle point without cloud spend | 1–2+ weeks of exclusive CPU occupancy for a model inside Stage 2's capacity class; low marginal value over (b). Not recommended. |
   269→
   270→This plan does not assume any unowned hardware. The only resource claim it makes: IF a single modest GPU is rented for a day, Nano's compute is hours, not months — the true prerequisite is the 100M-token licensed corpus, which is a data-engineering project measured in weeks, not a compute project.

   305→### 9.2 Formulas (all derived numbers in this document use these)
   306→
   307→1. **Params** (bias=b ∈ {0,1}, RMSNorm, tied): `P = V*C + T*C + L*(12*C^2 + (2+9b)*C) + C`; untied adds `V*C`. Verified: debug = 1,349,248 exact; debug-untied = 1,873,536; repo nano preset (L=8) = 34,124,288; proposed Nano (L=13) = 49,881,088.
   308→2. **Checkpoint bytes**: `≈ 12*P + ~65 KB` (fp32 weights 4 + AdamW 2 states 8 = 12 B/param). Measured: 16,256,510 = 12*1,349,248 + 65,534 → 12.049 B/param.
   309→3. **Training FLOPs**: `≈ 6*N*D`, true `≈ 6*N*D*(1 + T/(6C))` (causal attention term: 12*L*T*C*D vs weight term 72*L*C^2*D). Stage 0 measured-context check: 6*1,349,248*2,457,600 = 1.99e13; achieved ≈ 42.4 GFLOP/s (6ND basis) over 469.5 s.
   310→4. **Throughput**: `tok/s ≈ 5,234 * (N0/N) * u`, u bands [0.5,0.9] / [0.4,0.8] / [0.3,0.7] for Stages 1/2/3; per-token 6N = 8.10 / 30.4 / 95.8 / 299.3 MFLOP for Stages 0–3.
   311→5. **RAM**: `R ≈ 16*N + L*4B*(19*T*C + 3*H*T^2) + 12*B*T*V + 0.4–0.6 GB runtime`. (19*T*C = saved per-layer activations incl. residual streams, norms, qkv, attention output, FFN hidden and GELU output; 3*H*T^2 = attention matrix copies; 12*B*T*V = logits + log-softmax + grad.) The activation constant is a rough engineering factor — treat RAM numbers as ±30% ESTIMATE until each stage's `ram_report` measures it.
   312→6. **Chinchilla reference**: D_ref = 20*N (upper reference only; small LMs are usually overtrained beyond 20:1 when data allows; current corpus permits neither case).
   313→7. **Epochs**: D_processed / D_unique_train. EXP-001: 2,457,600 / 230,168 = 10.68 (derived from measured numbers).

Effective-throughput band 10–40 TF/s reflects modest MFU of a 50M-parameter fp32-origin codebase; 100–200 TF/s is quoted as the optimistic hardware ceiling, not the plan basis.
